## Findings and fixes

**Provider failure must not hide earlier committed recordings.** Phantasy Tour
returned HTTP 403 on the first page for Lotus and the Disco Biscuits, exhausting
five attempts for each. Their earlier Archive work had already finished, but the
artist workflow skipped rebuilding after the later provider failed. The updated
coordinator rebuilds shows, years, and cache before propagating an ordinary
provider failure. Failure before the artist plan is prepared, cancellation,
and expiry still stop without rebuilding. Separate standalone rebuilds for both artists completed
during the measurement window.

Archive metadata updates also cleared an existing recording's show association
until the final rebuild. They now retain that association when the display date
is unchanged. A moved recording still waits for rebuilding to join its new show.
An integration test reads playable tracks before rebuilding and verifies stable
recording and track identities after both cases.

**Malformed dates must not stop an entire artist rebuild.** A lowercase `xx`
month on a Yes recording reached PostgreSQL's date conversion and failed on every
retry. Rebuilding
now handles `XX` and `xx` consistently and preserves the display label and show
identity. An unknown month sorts on January 1; an unknown day sorts on the first
of its month. Invalid dates remain on source records without preventing valid
recordings from rebuilding.
Actual PostgreSQL tests cover partial dates, invalid dates, healthy sibling
shows, and repeated rebuilding.

**Repeated review identities need one upsert input.** Phish.net completed 1,889 of
1,893 source enrichments; four failed because a review batch attempted to update
the same database UUID twice. The shared review service now deduplicates by its
existing UUID before the upsert. The last supplied review body wins. A real
Archive import regression verifies duplicate handling, removal of absent reviews,
distinct reviews, and stable row IDs and UUIDs on reimport. The affected Phish
shows are April 28, 1990; July 8, 2003; July 9, 2014; and September 4, 2016.

**Repeated small catalogs inflate workflow history.** One completed Phish.in run
contained the same 34,856-byte song lookup in 93 activity inputs: 3,241,608 bytes
of its 4,717,851-byte history, about 69%. The existing Redis codec kept these
values inline because its cutoff was 256 KiB. The cutoff is now 32 KiB, so the
lookup reuses one content key while typical show inputs remain inline. This saves
history storage; each use still serializes the value, refreshes its Redis expiry,
and reads it for decoding. Tests cover a realistic 35 KiB shared value through
activity handoff, worker restart, continuation, and replay, alongside the existing
large-message case.

The worker now emits JSON console logs. Its previous formatter rendered dictionary
scopes as type names, losing the workflow, artist, provider, and attempt fields
needed to correlate item failures.

## Deletion guard alert correction

A later review of the run’s Discord alerts found a counting bug that the initial
verification missed. The channel history covering the run contained 75 alerts:
72 reported zero deletion candidates, two reported one, and one reported two.
All were below the five-recording limit printed in the message.

The workflow was retaining new upstream items with no VBR MP3 files as deletion
evidence, even though those items had never created recordings. Six such skips
filled its bounded checkpoint and activated a second check on the raw skip count.
This could suppress a legitimate small cleanup as well as send a false alert.

Exact original histories confirm the distinction. Scott Metzger had nine new
unplayable skips, Tonic had eight, and Grateful Dead had 185 plus 35 completed item
imports. All those no-MP3 skips had a null stored source ID. Each guarded deletion
plan had no decisions and applied no deletions; successful imports were retained.
The one- and two-candidate alerts establish deferred verification, not proof that
those recordings had disappeared upstream.

Fix `0a5b85e` retains no-MP3 evidence only for stored recordings and applies the
limit to actual catalog candidates. The six-recording checkpoint bound, the
five-deletion guard, and independent upstream verification remain. Six focused
integration tests passed, including zero, one, and six stored recordings mixed
with six new unplayable items. An independent source review found no actionable
issue. The live no-alert check and deployed images are recorded in the operating state
below.

## Throughput and capacity

The first batch segment drained to Phish alone while it finished Phish.net. The
other provider queues were idle before the next 250 artists started. This is a
consequence of draining a segment before continuing, without a database lock
or worker queue backlog. Later segments processed roughly 60 artists per minute.
The 250-artist drain rule costs some time when one artist has much more work;
retain it for now because it keeps continuation ownership simple.

A completed artist with an empty Archive selection took 9.995 seconds. Discovery
used 9.768 seconds; preparation, deletion checks, and each rebuild used 8–12
milliseconds. Activity queue waits were about five milliseconds. This sample
places the delay in discovery. Matching worker logs show 9.758 seconds between
the Archive search request and its HTTP 200 response headers, leaving about ten
milliseconds for the other discovery work. This sample is limited to one artist;
the previous log format did not expose explicit correlation fields.

Across 78 periodic samples, readiness took 0.132–0.629 seconds and fresh public
show requests took 0.204–0.533 seconds. No sampled listener request failed. The
primary had at most 32 client sessions, with no observed blocking, lock waits,
new deadlocks, or temporary spills. Maximum sampled replica lag was 115 ms.
Application rollbacks were confined to the known input failures.

Temporal peaked at 908 MiB RAM and the worker at 345 MiB. Sampled node CPU peaked
at 42% and memory at 53%; a separate initial CPU observation was 49%. Minute
samples can miss shorter peaks. Payload Redis reported no evictions, rejected
connections, or delayed AOF writes. No capacity increase is justified by this run.

Actual database size grew by 17.46 MiB for `app`, 214.61 MiB for `temporal`, and
226.91 MiB for `temporal_visibility`. Disk growth includes database and index
storage; it is not the same measure as reported history bytes. These observations
cover one run. They do not establish a seven-day steady-state retention size.

# Playlist discovery and Sonos updates

Proposed for review · November 27, 2026

1. **Playlist discovery.** Show followers and listening activity on public playlists and use those numbers in browse and search. Ship the API, mobile, and web changes together.
2. **Sonos queue edits.** Wake a Temporal workflow when someone edits a room's queue so busy or slow rooms can be handled concurrently. This phase can ship on its own.
3. **Sonos room names.** Keep Now Playing current when speakers regroup. This needs the group-name sync in `a30b8db71` merged first, the Phase 2 worker, and a mobile update to use the server's name.
4. **Sonos plays.** Record qualifying listens in account history and catalog popularity independently of the queue and room-name work. Playlist attribution needs a mobile release that sends playlist IDs with queue items.

## Phase 1 · Playlist metrics

### What listeners see

Public directory cards, the shared playlist page, owner cards and detail, followed cards, and search cards all show `follower_count` and `popularity` for public playlists. Zero followers is a count. If the popularity job has no row for a playlist, return null for `popularity` and `popularity_as_of`. When a row is present, `popularity_as_of` gives the UTC cutoff and the windows can show zero activity. Label the metric “track plays” so a listener who starts five tracks understands what is counted.

The directory defaults to **Recent**. **Most followed** sorts by followers and **Most played** sorts by 30-day track plays. Public playlists with zero activity can appear in browse and search.

Use the existing API routes. Extend their resources and replace `recent_play_count` with `popularity.windows["30d"].plays`. Search fills its existing top-level `popularity`. Ship the API, mobile, and web contracts together. Fetch metrics on online reads. Follower count and play snapshot changes leave playlist content revision and update time alone.

### Where the numbers come from

- **Follower count.** Store `follower_count` on `user_data.playlists`. Reads and the playlist index use that column. Index `(follower_count DESC, id DESC)` for Most followed.

  Backfill from `playlist_follows` and install a trigger in the same migration with follow writes blocked. The trigger adjusts the count in the same transaction for each inserted or deleted follow row. This covers deletes from account purges as well as unfollows. A retained follow for a deleted playlist has no counter to update.

  Have the follow path lock the playlist `FOR NO KEY UPDATE` before inserting. With today's `FOR SHARE`, two concurrent follows could each hold a share lock and wait for the other before updating the count. [Follow relation](../../RelistenUserService/Persistence/Configurations/PlaylistSharingConfiguration.cs) · [Follow transaction](../../RelistenUserService/Playlists/PlaylistSharingService.cs) · [Current playlist lock](../../RelistenUserService/Playlists/PlaylistVisibility.cs)
- **Play windows.** Use the Catalog API's existing 48h, 7d, 30d, and 1y windows. The nightly job refreshes the last three complete UTC days before reading `source_track_plays_playlist_daily`. A quiet day can leave the aggregate watermark unchanged, so the job publishes through the UTC cutoff it just refreshed. The 48h window covers two complete days. Count late uploads on the UTC day the catalog receives them. They enter the rollup when it materializes that day, leaving the older playback day alone. Sum catalog track durations for estimated hours, as catalog Popularity does. Copies have their own IDs and metrics. [Playlist play rollup](../../RelistenApi/Migrations/Sql/024_playlist_plays.sql) · [Materialized-only policy](../../RelistenApi/Migrations/Sql/025_playlist_plays_materialized_only.sql) · [Catalog receipt time](../../RelistenUserService/History/PlayHistoryUploads.cs#L60)

Use the same `PopularityResource` for catalog and playlists so playlist cards and pages can show the same Popularity view as catalog items. Each playlist snapshot includes `momentum_score`, `trend_ratio`, and plays, hours, and `hot_score` for `48h`, `7d`, `30d`, and `1y`. Momentum, trend and hot scores remain non-nullable doubles. Catalog continues to omit `1y` where annual stats are unavailable.

Calculate playlist momentum from the daily rollup. Reuse the existing scoring weights and percentiles, with one input changed. Compare plays on the latest complete materialized UTC day to the average per day over the seven days ending that day. Catalog uses a six-hour window for that part of the score. The daily version reacts to day-to-day changes and smooths out spikes within a day. Hot score and the 48-hour trend versus the 90-day baseline use the existing calculations. The nightly job can read all inputs from the same grouped rollup query. [Catalog momentum weights](../../RelistenApi/Services/Popularity/PopularityService.cs#L1449)

Playlists with activity in the past 30 days form the population for momentum percentiles. A playlist with annual plays and no 30-day activity returns zero momentum, as catalog detail does. All scores describe the snapshot at `popularity_as_of`.

Move the three Popularity DTOs to `Relisten.Search.Contracts` and reference them from `Relisten.Accounts.Contracts`. Add the Newtonsoft reference to the shared project. Use explicit window keys and omit an unavailable `1y` window with both Newtonsoft and System.Text.Json. The nightly calculation stays in the Catalog API. ### Search and play reporting

The playlist index build calculates a past-year play percentile across public playlists, using the same window catalog search uses for songs and performances. Zero plays or a pending snapshot gives zero play boost. Retrieval sorts by text match, then past-year plays, then followers, while final ranking combines relevance with the play percentile, preserves exact library title priority, and uses followers to break ties between equally ranked playlists. Search continues to check current visibility. The directory's Most played sort uses `30d`, the default window for catalog Popular Shows. That gives listeners a way to browse recent activity. The directory reads the daily snapshot directly. Search picks it up on the next playlist index build. [Catalog Popular Shows](../../RelistenApi/Controllers/PopularityController.cs#L44)

The anonymous endpoint checks the format of a supplied playlist ID, so reported play counts can be inflated. Improve validation at ingestion so the same correction flows to search, the directory, and cards. [Catalog play write](../../RelistenApi/Services/Data/SourceTrackPlayService.cs)

Verify the two windows with a pair of equally relevant public playlists whose 30-day and past-year counts sort in opposite directions. The directory should favor the one with more recent plays. Search should favor the one with more past-year plays. Include an exact library title and a public playlist with no plays to verify their existing paths.

## Phase 2 · Deliver Sonos queue edits through Temporal

Relisten has about 100,000 users. Alec expects tens of thousands of active Sonos queues at peak once Direct Control ships. For sizing, assume 20,000 queues average one edit every 10 minutes at peak. That is `20,000 ÷ 600 ≈ 33` edits per second, about eight times what a single poller can deliver when each edit needs a refresh. Coalescing edits to the same queue reduces the refresh rate.

The poller takes the eight oldest due queues every two seconds, for at most four refreshes per second per replica. It refreshes them serially and holds the room and grant locks in a transaction during the Sonos call. At 300 ms per call, eight take at least 2.4 seconds, so that drops to roughly 3.3 refreshes per second. One slow room delays the rest of the batch. Replicas can select the same eight rows. The later replica waits on the lock and can then find the refresh already done. [Current poller and refresh](../../RelistenUserService/Sonos/SonosQueueRefreshCutoverPoller.cs)

Wake a Temporal workflow for each edited queue and allow different queues to refresh concurrently. At an assumed 300 ms per Sonos call, `33 × 0.3 ≈ 10` concurrent calls cover the steady-state estimate before database and scheduling overhead. Start with eight refresh activity slots per replica and two replicas. That gives 16 slots for the estimated load, bursts, and retries. Watch the age of the oldest due edit and Sonos throttling before increasing the cap.

Add one `sonos` task queue in the existing `relisten` namespace. Each of the two User Service pods hosts a worker with eight activity slots. The workers share the task queue, account database, Sonos client configuration, and Data Protection setup. Phase 3 uses the same task queue for its household workflows. Workers restart after a polling failure and shut down with their pods. [User Service registration](../../RelistenUserService/AccountsApplication.cs)

1. **Signal before committing the edit.** Under the existing room and grant locks, save the replacement, version, and command receipt in the edit transaction. For a changed order, call Signal-With-Start on `sonos-queue-refresh-{queueId}` under a short deadline, starting with one second. Once Temporal confirms acceptance, commit and return the receipt. Delivery to the speaker stays asynchronous. If the signal RPC fails or times out, roll back and return a retryable `503`. Mobile already retries once with the same `command_id`. A retry after the edit committed returns its original receipt. A retry of a rolled-back edit still has to pass the usual version and playhead checks. [Queue edit transaction](../../RelistenUserService/Sonos/SonosPlaybackController.Queue.cs#L108) · [Mobile retry](https://github.com/RelistenNet/relisten-mobile/blob/49b3cb2464ae0f2f990acb220e0e2f651a3bd363/relisten/sonos/sonos_room_store.ts#L675-L695) · [Temporal Signal-With-Start](https://docs.temporal.io/glossary#signal-with-start)
2. **Refresh the latest committed version.** The activity takes the same locks before it decides whether a version needs delivery. If it runs while the edit is open, it waits, then sees the committed version or the prior state after rollback. This lets a signal accepted despite an RPC timeout finish harmlessly. Coalesce edits to the same queue and reread if a signal arrives during delivery. Under the locks, check that the queue and grant are still valid and refresh only if its committed version is ahead of the acknowledged version. Rereading that version also makes activity retries safe. If Sonos handled the refresh but the acknowledgement was lost, a repeat notification can make the room fetch the same or a newer order. It leaves the edit itself applied once. [Sonos queue refresh command](https://docs.sonos.com/reference/playbacksession-refreshcloudqueue-sessionid)
3. **Let Temporal retry delivery.** Retry transient failures for up to five minutes, honoring Sonos's retry delays within that window. A Sonos 401 refreshes the grant once before trying delivery again. A missing session retires the queue. Other permanent rejections clear the pending marker without advancing the acknowledged version. When transient retries run out, the saved edit stays unacknowledged and still reports pending. A later edit can start another delivery attempt. [Temporal activity recovery](https://docs.temporal.io/durable-execution)

   A Sonos acknowledgement records the sent version. The room's observed version separately confirms it fetched the order. During the rollout, the cutover poller covers writes from old API pods. The pending marker and the gap between committed and acknowledged versions determine whether delivery is needed. Turn the poller off once all writers signal and pending edits from old pods have drained.

If Temporal is unavailable, a queue edit fails with a retryable `503`. Each changed edit holds its room lock and a database connection for up to the one-second signal deadline in addition to its existing work. At the assumed peak, Temporal receives about 33 Signal-With-Start calls per second. That can start up to 33 new runs per second, with fewer starts when edits coalesce into a running workflow.

Set `Sonos__LegacyQueueRefreshEnabled=true` on the first rollout to keep the old poller during the transition. After the old pods are gone, let it deliver any remaining edits those pods accepted, then turn the setting off. It defaults to off.

**Done when** an unavailable Temporal service returns a retryable error and leaves the order unchanged. Retry the same command after Temporal returns and verify one committed edit and delivery. Let the activity start before a commit and before a rollback and check that the room only gets committed edits. Verify that an edit arriving as the workflow finishes still reaches the room, and that Temporal retries a worker failure after commit. A replaced or revoked queue must never receive a stale refresh.

Exercise the assumed peak of roughly 33 edits per second with a simulated Sonos endpoint and include a slow room. Verify that other rooms keep receiving edits and that concurrency stays within the cap. Aim for edit-to-acknowledgement p95 around two seconds and measure edit-to-observed-version separately. On real hardware, verify that the newest edit reaches the room.

## Phase 3 · Propagate Sonos room names

The name sync from `a30b8db71` is included in Phase 3 and makes GET groups save current names before responding. Household callbacks reuse that update. Each update sets only names on matching loaded or dispatching queues for the authorized account and household. Missing groups go through normal playback reconciliation.

Verify a real regroup callback before setting `Sonos__HouseholdEventsEnabled=true`. Use the existing Sonos callback signature checks. Extract the signed household target or map a signed group target to a known household. The separate household header and JSON body are outside the signature. An authorized `getGroups` read supplies the names. On the Phase 2 Temporal worker, run one workflow per affected household to coalesce events and reread for each linked Relisten account with a live queue there. Renew subscriptions on authorized discovery or handoff. The household workflow tries the refresh up to three times. GET groups remains the recovery path after those attempts or a missed callback. [Household subscription](https://docs.sonos.com/reference/groups-subscribe-householdid) · [Callback delivery](https://docs.sonos.com/docs/subscribe)

Mobile commits `126ed0a0` and `49b3cb24` use room-list names on Play On, foreground, and launch restore. Once GET groups persists names, remove the override in `apply` and `withListedName`. Keep list names for the room picker. Have `refreshPlaybackAfterRoomList` refresh playback if the room's listed name differs from the displayed playback name or its ID is missing. An older in-flight playback read may briefly show the old name. Follow it with one read after GET groups has saved the name, provided the same account and playback handle are still active. No new playback poll is needed.

**Done when** a regroup with the same group ID changes Now Playing without a handoff. A delayed list cannot overwrite a newer playback name. A missing room still gets a playback read. Check launch restore and foreground against the shipped mobile behavior, then verify a duplicate or missed event and household scoping with two linked accounts.

## Phase 4 · Record Sonos Cloud Queue plays

Accept one extra play on a phone-to-Sonos handoff if local playback already counted and the speaker independently reaches the threshold. For example, a 12-minute track moved at minute four can count on the phone and again after four minutes on Sonos. The phone skips reporting while it is the Sonos controller. Relisten still deduplicates reports of the same speaker playback. [Mobile reporting guard](https://github.com/RelistenNet/relisten-mobile/blob/49b3cb2464ae0f2f990acb220e0e2f651a3bd363/relisten/player/relisten_player.tsx#L752-L764) · [Handoff start position](https://github.com/RelistenNet/relisten-mobile/blob/49b3cb2464ae0f2f990acb220e0e2f651a3bd363/relisten/sonos/sonos_handoff.ts#L74-L85)

On November 27, production returned HTTP 204 for a `timePlayed` callback about one second after a skip on Alec's Office. The deployed handler authenticated the callback and discarded its body. Capture a redacted report from a real speaker before release to verify the item ID, playback report ID, and duration. [Sonos report fields](https://docs.sonos.com/reference/v23-item-attributes)

1. **Save where each item came from.** Extend `SonosOccurrenceInput` and mobile's `wireOccurrences` with optional `playlist_id` and `playlist_entry_id` alongside `occurrence_id` and `track_id`. Both handoff and queue-edit requests use this occurrence shape. Save the IDs with the Sonos item ID and resolved recording. If the same track was queued from two playlists, credit the playlist that supplied the item that played. Older app versions still record qualifying plays in account history and catalog totals. Without the new fields, those plays carry no playlist attribution. [Server occurrence input](../../RelistenUserService/Sonos/SonosHandoff.cs#L20) · [Queue edits](../../RelistenUserService/Sonos/SonosPlaybackController.Queue.cs#L8) · [Mobile occurrence serialization](https://github.com/RelistenNet/relisten-mobile/blob/49b3cb2464ae0f2f990acb220e0e2f651a3bd363/relisten/sonos/sonos_playback.ts#L84)
2. **Apply mobile's thresholds to time played.** Authenticate the queue and resolve the item in its saved or retained removed items. Count once per Sonos `reportId` when cumulative `durationPlayedMillis` reaches half the track or four minutes, whichever comes first. [Mobile thresholds](https://github.com/RelistenNet/relisten-mobile/blob/49b3cb2464ae0f2f990acb220e0e2f651a3bd363/relisten/player/relisten_player.tsx#L752-L764) · [Sonos report fields](https://docs.sonos.com/reference/v23-item-attributes)
3. **Claim the report and reuse the play writer.** Give `user_data.sonos_playback_reports` a primary key of `(queue_id, report_id)` and cascade deletes from the queue. On a qualifying report, `INSERT ... ON CONFLICT DO NOTHING` and write through `PlayHistoryUploads` in the same transaction only if the insert won. A report below the threshold leaves its ID available for a later qualifying update. The claim survives an intervening replay and avoids rewriting the queue's items JSON. A stable `play_id` alone is insufficient because the play writer's conflict key also includes `qualified_at`. Use the existing Sonos app type and put the saved playlist ID on the catalog event. Sonos plays count regardless of the phone's Listening History setting. [Queue storage](../../RelistenUserService/Sonos/SonosRows.cs#L23) · [Account and catalog write](../../RelistenUserService/History/PlayHistoryUploads.cs#L32)

**Done when** a short skip produces zero plays and a qualifying listen produces one history row and one catalog play for the correct playlist. Exercise a valid retry of A after replay B, with a different arrival time, and verify two plays total. Confirm that a qualifying listen without playlist metadata still reaches history and catalog totals.

On hardware, confirm that reports for the same playback share an ID and that replay produces a new ID. A final `timePlayed` report can arrive for up to five minutes after eviction or expiry, with the original queue credential and an active session. Confirm the report arrives in that window on hardware. Confirm the catalog play reaches the playlist rollup after materialization.

# Build and review v4 in five checkpoints

Build one maintained catalog core, prove its responses first, then connect mobile.
Keep the account/auth conversion as a separate deployment. Each checkpoint gives
Alec something running to inspect before the next dependent work expands.
This is a review guide for Alec and Switz. C1 is now implemented for local review;
start with the [real response examples and running API](review/README.md).
C2–C5 remain unimplemented.

## The simplification to preserve

Common catalog readers own imported facts, normalization policy and relationships.
Native v4 resource models define the maintained public contract. V2/v3 adapt
their inputs and outputs around that core. Convert legacy families individually,
after their v4 responses are accepted and legacy fixtures protect their behavior.
Do not rewrite ingestion or unrelated data-service callers to finish a shim.

Mobile keeps one Realm and repository set. Its v4 adapter converts API IDs and
applies normalized overlays to the existing catalog. Existing UUID keys still
identify downloaded files, queues and history. Account/auth IDs become canonical
typed strings, including storage, while framework and provider IDs retain their
existing meanings. These boundaries keep conversion out of feature code.

Ordinary responses are direct resources or lists. Every track has one
`normalization` object; its imported playback title and file remain authoritative.
Use weak HTTP ETags over deterministic JSON for refresh. Endpoint contracts
define which associations mobile replaces. There is no generic response metadata
or new synchronization engine to understand before writing a feature.

Some work now reduces repeated work later: shared typed-ID fixtures, one track
projection, transactional mobile apply, real HTTP tests, and native account IDs
before public rollout. The account conversion is substantial, so isolate its
migration and re-sign-in rehearsal from catalog activation.

Keep these out of this implementation: a writer epoch, v4 response-cache
invalidation system, generic repository/endpoint framework, catalog storage-ID
migration, player-identity migration, or favorite-merge orchestration. Their costs
do not help deliver the approved behavior. Measure primary reads before adding
caching; exact-target favorites keep merge behavior small.

## C1 — Inspect the first real HTTP responses

Implement packages 1 and 2 for artist/year/show-list navigation, show detail,
direct source and track reads. Alec expanded C1 to review these with the venue
family before auth: artist venue groups, canonical metadata and show collections,
and imported venue fallback detail. The current local API exposes 16 GET routes.
Cover raw, normalization-disabled, partial and fully interpreted
fixtures. Alec reviews each family before its contract spreads to the next family
or mobile work.

Use the [venue-to-playback walkthrough](review/venue-source-journey.md) for the
current review: artist → venue group → venue's shows → show → source → track.
Then add the next song/discovery slice for API review. Song discovery, search,
recent lists, and artist bootstrap are not implemented by the venue slice.
Keep account/auth as a separate checkpoint after the catalog responses settle.

Deliver a repeatable local review setup using the real development API,
controllers, serializers and readers. Alec required real data, so manual review now uses a freshly restored production
catalog in the standard local database. Synthetic fixtures remain confined to
disposable regression-test databases. Review startup never resets catalog data.
Run no provider imports or background workers to populate review data.

The planned review outputs are:

- Running Swagger UI at `/api-docs-v4` and OpenAPI JSON at
  `/api-docs/v4/swagger.json`, with the local base URL printed at startup.
- A checked-in `.http` request collection, proposed as `review/requests.http`
  alongside this guide. It supplies named fixture IDs from the fixture builder;
  Alec does not invent or copy suffixes between requests.
- Actual JSON and header captures generated by those requests, plus one
  documented launch/reset command. Captures record evidence; DTOs and tests
  remain the contract source. Do not build a separate demonstration API.

The request collection and response captures are now available for C1.
Default requests are reads. Operator command examples stay in a separate
collection exercised against inert test dependencies; they start no imports.

Alec should be able to answer these questions by making requests:

- Are IDs named and formatted consistently, including parent references?
- Is the original playable title obvious? Are ordered normalized parts useful
  without suggesting that a part is another file?
- Are raw, disabled and partial results understandable and still playable?
- Does the show preserve its imported venue label/locality, with a normalized
  venue link and typed aliases when available?
- Do grouped venue counts match their show collections, including imported
  fallback and cross-artist approved assignments? Does direct source detail match
  that same source inside its full show?
- Are wrong prefixes, unknown IDs and dependency failures clear?
- Does an unchanged request return 304? Does a local normalization correction
  return 200 with a changed ETag despite unchanged imported timestamps?

Review compressed and uncompressed responses too. Mobile only needs equality
validation; weak ETags avoid coupling the JSON hash to compression details.
Record the accepted build, scenarios and any requested response changes in the
existing plan Progress section. Do not expand the contract while that feedback
remains unresolved.

## C2 — Rehearse the account/auth change independently

Convert owned account/auth IDs and `/v1/library` in place. Prove the typed mobile
account client against today's v3 imported catalog. Normalized Realm models and
v4 catalog activation are not prerequisites for this checkpoint.

In a disposable migration rehearsal, preserve users, provider links, usernames
and favorite memberships. Retire old sessions/token families, sign in again,
and confirm the same account and favorites return. Check profile IDs against
token claims; exercise refresh, logout, account switching and mutation replay.
Test interrupted mobile credential clearing and restart recovery.

Imported catalog hearts must produce typed imported targets before reaching the
library repository, even while v3 serves catalog data. Test anonymous favorites
and discarded alpha outbox recovery. Keep downloads, queues and history intact.

Alec reviews a tester sign-in and favorite round trip, migration invariants,
and the deployment/forward-fix procedure. Deploy this breaking change in its
own account/auth window. Do not combine it with catalog activation.

## C3 — Prove the smallest mobile catalog integration

After the C1 response review and isolated C2 account proof, connect raw and
normalized show/track reads to the shared mobile storage and player. Accept
this pilot before expanding all v4 route families. A local read/playback pilot
needs no account login; account deployment and catalog activation stay separate.

Alec opens both shows, switches source, plays a track and inspects normalized
details. Apply a normalization-only correction and verify canonical links and
alias details refresh while the imported venue label stays unchanged.
Test offline restart, unchanged file paths, queue/history restoration and a
failed apply followed by retry. Data and applied ETag commit together.

Keep catalog fallback usable in the upgraded build. A successful pilot proves
the response-to-storage mapping; it does not qualify complete API coverage.

## C4 — Finish and review the complete API

Expand one resource family at a time, reusing accepted track and parent-resource
models. Convert its legacy reads into bounded compatibility adapters with
pre-change response and performance fixtures. Avoid one large legacy rewrite.

Extend the same request collection and Swagger examples. Alec reviews artist
bootstrap, grouped venues, typed venue aliases, raw song fallback, exact normalized
song → show/source/track matches, resolver results, search and recent lists.
Normalization corrections must not change the recording-based meaning of
recently updated. Review operator inputs/results through inert tests separately.

Compare actual actions/OpenAPI against all entries in [endpoints.json](endpoints.json).
Show response captures and coverage results together. Full capability coverage,
legacy compatibility and shared-core readability must pass before completing
the mobile browse and library UI. Route count alone is insufficient evidence.

## C5 — Complete mobile and qualify the release

Finish normalized browse, global venue detail and the separate My Library Venues
section. Test raw artists alongside approved and partially normalized artists.
Venue favorites span artists; they do not implicitly favorite shows. Keep the
agreed simple behavior for merged/retired exact favorite targets.

Alec reviews the end-to-end mobile journeys, including schema upgrade from
existing data, offline cold start and v3 catalog fallback with typed accounts.
Attach full API coverage, migration results and representative performance
measurements. Agree primary-capacity/latency budgets before expanding traffic.
Rehearse each applicable rollback with the schema-compatible builds.

## How to keep the work reviewable

Use separate changes for the first HTTP contract, account/auth conversion,
mobile pilot, subsequent API families and final mobile integration. Independent
server work may proceed after its prerequisite contracts settle. Approval at a
checkpoint covers the recorded behavior; deployment remains a separate action.

For each checkpoint, Alec needs the running build or test result, a short list
of scenarios to inspect, changed responses, and unresolved issues. Record the
outcome in the existing plan; no additional approval workflow is needed.

The [plan overview](README.md) maps these checkpoints to implementation packages.
[Contracts](contracts.md) defines behavior; [verification](verification.md)
defines tests, migration and release evidence. Start with C1. If its responses
need revision, fix them before account and mobile work depends on them.

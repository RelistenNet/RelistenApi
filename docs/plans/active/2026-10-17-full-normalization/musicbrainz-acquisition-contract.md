# Bounded MusicBrainz acquisition

`NormalizationMusicBrainzInputService` acquires the three fixed lookup representations supported by the [pure decoder](musicbrainz-decoding.md). Its receipt store and provider gate acquire external source assertions only. Typed [search pages and their frozen operator plans](musicbrainz-candidate-search.md) now share this transport/store/gate; the command signatures below describe the lookup path. Catalog links, identity acceptance and recurring scheduling remain separate work.

## Existing components and gaps

`NormalizationEvidenceService.CaptureInputAsync` already retains exact bytes, deduplicates revisions, replays a stable fetch UUID and compares the generation read before HTTP. Every admitted fetch advances generation, including equal bytes. Keep that behavior. `GetCaptureAsync` can recover a committed fetch without repeating HTTP.

`NormalizationProviderInputService.FetchAsync` generates its fetch UUID internally, returns only the parsed value and can bypass evidence when capture is disabled. It has no durable request preparation or HTTP receipt. The MusicBrainz adapter composes `NormalizationEvidenceService` directly and always retains evidence; the existing importer behavior is unchanged.

`IngestionHttpHandler` disposes 429/5xx responses before retention. Temporal limits activities rather than individual HTTP requests, and direct API/CLI callers bypass its queues. The adapter uses a dedicated named HTTP client. `DbService` retries database callbacks after serialization failures/deadlocks; never put HTTP in such a callback. Session advisory locks also do not fit the configured transaction-pooling path.

## Public command

Public types and service signatures:

```csharp
public sealed record MusicBrainzLookupRequest(
    MusicBrainzLookupKind Kind, // Work, Recording, Artist
    Guid Mbid,
    MusicBrainzCacheMode CacheMode, // ReuseFresh or Refresh
    TimeSpan? MaximumCacheAge);

Task<MusicBrainzAcquisition> AcquireAsync(
    Guid commandUuid, MusicBrainzLookupRequest request, CancellationToken ct = default);
Task<MusicBrainzAcquisition> ResumeAsync(Guid commandUuid, CancellationToken ct = default);
Task<MusicBrainzAcquisition?> GetAsync(Guid commandUuid, CancellationToken ct = default);
```

`ReuseFresh` requires an explicit positive maximum age; `Refresh` has no cache age. Do not invent a production freshness interval. Freeze the normalized request and acquisition version before the first network operation. Reusing a command UUID with a different request conflicts. Exact terminal replay returns its original result, including results produced by an older supported implementation, without HTTP or new capture. Perform terminal replay before current-version compatibility checks. An unfinished unsupported profile fails explicitly rather than being interpreted with new defaults.

An acquisition is `Pending`, `Completed` or `Failed`. Pending includes its next eligible retry time. Completed identifies `Cached` or `Captured` and returns the original input reference, fetch UUID and resource generation observed by this command. Load raw bytes through `NormalizationEvidenceService.GetCaptureAsync` when needed. Failed retains its reason and all attempt receipts; stale captures, HTTP failures and uncertain requests remain distinguishable. Returning a capture never promises that its input remains current after return. Downstream Work admission/publication still checks its original input clocks.

Each command permits at most three dispatched HTTP attempts, including uncertain attempts. Each Acquire/Resume invocation drives at most one GET and never sleeps through cooldown; the caller resumes a Pending command at or after `NotBefore`. Each attempt gets a separate persisted UUID, also used as its evidence fetch UUID. Resume continues the saved phase and budget. Transient transport errors, 429/5xx, lost admission and stale CAS may retry within that budget; each retry obtains a new permit and reads a new generation before HTTP. Invalid representations, unsupported statuses/profiles, oversized responses and ordinary 4xx responses terminate without automatic retry. A later explicit new command can try again.

## Preparation, HTTP and capture

1. **Read or create the frozen command.** Reject ambient transactions and invalid MBIDs/profiles before HTTP. Construct exactly the three fixed HTTPS URLs and `inc`/`fmt` profiles in the decoder guide; callers cannot supply arbitrary URLs or query parameters.
2. **Try the retained cache.** On the primary, read the current input and its latest admitted fetch in one snapshot. Require the exact profile/capture version and a successful adapter receipt for that fetch, with original observation time inside the requested age. A matching revision alone is insufficient provenance. Save that cache decision and original capture reference as the command's result. Cache hits perform no capture and advance no resource generation.
3. **Claim network admission after the cache check.** The cache check runs under the shared gate/command locks, so it sees a peer capture completed while this command waited. On a miss, persist the attempt's request URL, parameters, User-Agent, capture version, expected resource generation and absolute deadlines before sending. Never replace this generation after receiving the response.
4. **Claim dispatch, then send one bounded GET outside SQL.** In one short transaction, create the frozen preparation and unique `DispatchStarted` intent under the gate/command locks. Only the caller receiving that newly committed permit may send. Committing dispatch intent consumes one attempt, even if the process dies before an actual send. Concurrent Resume calls never resend a `DispatchStarted` attempt. Current bounds are a request timeout of at most 30 seconds, 8 MiB complete response body and 64 KiB normalized receipt metadata. The absolute HTTP deadline includes the prepared send window; the actual send uses the smaller of its remaining time and the configured request timeout. Use `ResponseHeadersRead`, a meaningful configured application/version/contact User-Agent and `Accept: application/json`. Disable automatic retries, redirects, cookies and decompression; request identity encoding. Unsupported content encoding is a retained failure, not reconstructed JSON. Do not send conditional requests in this first adapter; unexpected 304 is not a successful empty representation.
5. **Save an immutable response receipt.** Retain exact complete bounded bytes, status, final URL, timestamps, byte count and SHA-256. Allowlist only provenance/backoff headers: `Content-Type`, `Content-Encoding`, `Content-Length`, `Date`, `ETag`, `Last-Modified`, `Retry-After`, `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`, `X-RateLimit-Zone`, `X-RateLimit-Who` and `X-MB-Rate-Limiter`. Omit cookies, authentication and unrelated headers. These are parsed values exposed by `HttpClient`, not raw wire framing. Overflow/incomplete transport retains bounded metadata and an explicit incomplete-body reason, without a fabricated full-body hash or truncated input revision.
6. **Validate and capture from the saved response.** Require HTTP 200, a UTF-8 JSON representation/profile and an exact matching root entity identity without a provider error. The adapter validates this small envelope directly; it must not invent an input revision UUID to invoke the citation-producing decoder before retention. After capture, the pure decoder consumes the actual retained revision. Its optional-field issues remain cited partial facts and do not establish completeness. Use the original bytes, expected generation, observation time and stable fetch UUID in `CaptureInputAsync`. `ProviderRevision` may carry a real ETag or Last-Modified value; HTTP Date and local observation time are not substitute provider revisions. Save its immutable receipt before acknowledging command completion.

Positive-capture eligibility requires the exact provider permit token, an unexpired lease and a response completed within the absolute HTTP deadline. Response saving itself also permits late, ineligible receipts. A response completed under valid admission can finish capture later, even after the gate has been released: that eligibility receipt is immutable. If admission was lost before response saving, retain the late response and original generation as evidence, but prohibit positive capture from that attempt. This avoids a check-then-capture race against an expiring live permit without adding a generic callback to EvidenceService.

New response receipts retain both the original sender wall time (`CompletedAt`) and the monotonic duration from preparation (`PreparationElapsed`). Eligibility checks the nonnegative duration against the prepared HTTP window, plus the matching token and unexpired database lease. It does not compare timestamps from two machines. An on-time HTTP completion can be saved after its HTTP deadline during the bounded persistence interval, provided the lease remains valid. Late durations remain retained as ineligible evidence.

For these timed receipts, use the immutable database `saved_at` as the capture's `observed_at` and cache-age clock. Authenticate that timestamp when finishing capture. Keep `CompletedAt` as original transport provenance. Older saved receipts without `PreparationElapsed` keep their original completion timestamp and eligibility during recovery; an already committed capture must not acquire a different observation clock. Response replay compares the complete original receipt, including any timing proof, before returning the saved result.

A normally admitted response saved earlier can still become stale while capture is delayed. Capture with its original expected generation; retain the resulting historical revision/fetch and never substitute a fresh generation. A crash after response saving resumes capture without GET. A crash after capture commit recovers using `GetCaptureAsync(attemptUuid)`. No downstream rollback can erase those independently committed facts.

## One provider-wide admission gate

Use one fixed PostgreSQL row for all MusicBrainz work/recording/artist traffic across API, workers and CLI. A global key safely overthrottles different egress IPs. Every controlled caller sharing an egress must use the same gate database; a second database or unrelated client is outside that coordination guarantee.

Claim the row in a short transaction using database time. Store one active attempt/token, a short send deadline, lease deadline and `not_before`. Grant only when no unexpired owner and no cooldown blocks it; otherwise return a retry time. Do not allocate future timestamp slots. Require a lease longer than the send window, absolute HTTP timeout and cleanup allowance; 45 seconds is the default for the 30-second request timeout and five-second send window. Configuration caps the send window at five seconds, request timeout at 30 seconds and lease at 60 seconds; the lease must exceed the combined send/request bounds by more than five seconds. Use database time to prepare the deadlines and check the live lease. In the call that creates the dispatch, sample a monotonic process clock immediately before reading database time. Measure the send window and HTTP completion against that elapsed duration. Query and commit delays consume the window conservatively. A resumed dispatch receives no new process-clock anchor and cannot send again. Recheck the send window immediately before `SendAsync`; host wall-clock skew cannot extend it.

The response-save transaction atomically retains the immutable receipt and max-updates `not_before` to its database time plus at least 1.25 seconds, extended by a valid later `Retry-After`. When ordinary receipt metadata overflows, retain at most the largest bounded delta and latest bounded absolute `Retry-After` date. Compare these two forms using database time when saving, rather than selecting one using the sender's wall clock. The same transaction clears only matching ownership; cooldown cannot be lost in a separate release step. A later response never shortens an existing cooldown. A late response that lost admission may still extend backoff monotonically, while remaining ineligible for positive capture. This serializes requests and prevents catch-up bursts. Cache decisions release an unused permit without inventing a request. Fail closed if admission storage is unavailable.

After an expired lease, automatically record an unsaved `DispatchStarted` attempt as uncertain and allow a new bounded attempt after the deadline/cooldown. Preserve an already eligible `ResponseSaved` receipt and resume its capture; expiry must not reclassify it as uncertain or send again. A late sender cannot overwrite another attempt's response or publish an eligible capture. Cancellation after send consumes an attempt because the server may have processed it. Cancellation before dispatch intent commits leaves preparation resumable; after that commit, the same attempt must never send again. Completed bytes should receive a short bounded persistence attempt independent of caller cancellation; failure leaves recovery uncertain rather than claiming retention succeeded.

This is an ordinary timeout/process-recovery contract, not exactly-once network delivery. A database lease cannot physically fence a process suspended between its final deadline check and sending. Environments requiring unconditional wire-level timing need one controlled egress sender; neither queue settings nor database leases alone prove that guarantee. Ordinary timeouts/crashes do not require operator abandonment.

## Persistence and ownership

Migration 43, `AddMusicBrainzAcquisition`, adds MusicBrainz-specific storage:

- **Commands/attempts:** immutable request/version and per-attempt preparation, bounded attempt count, mutable phase/lease ownership and first-winner terminal result. UUID replay compares exact frozen facts. Each transport attempt belongs to one command and has one stable evidence fetch UUID.
- **Response receipts:** one immutable row per attempt with complete bounded body when available, SHA-256, HTTP/profile metadata, original expected generation and admission eligibility. Unique attempt ownership prevents a late response replacing an earlier one. Successful bodies are stored here as well as in input revisions; that bounded storage duplication pays for capture recovery without another GET. Do not delete receipts to reclaim it.
- **Admission row:** the single provider token/deadline/cooldown record, with compare-and-swap completion. No Work subject or causal dependency is created for transport coordination.

No change to immutable input/fetch schemas or their CAS semantics is needed. Link successful results to existing `input_fetches.fetch_uuid`; failed HTTP bodies stay in the receipt store and never replace a successful input head. A 404 is a failed lookup, not authorization to retract an identity or conclude a complete negative candidate universe.

Implementation files: `NormalizationMusicBrainzAcquisition.cs` models; `NormalizationMusicBrainzInputService.cs` for the named phases above; a cohesive `NormalizationMusicBrainzInputStore.cs` for preparation/receipts/gate; migration 43; minimal named-client/DI registration in `IngestionServiceRegistration.cs`; `TestNormalizationMusicBrainzAcquisition.cs` using a fake HTTP handler and real PostgreSQL. No Temporal provider, general queue, shared HTTP framework or matcher policy is required for this increment.

## Verification and operations

The PostgreSQL/fake-HTTP fixture `TestNormalizationMusicBrainzAcquisition` covers exact request profiles, current cache provenance and age, equal-byte clock behavior, exact replay, cross-kind admission, concurrent Resume, response/capture recovery, stale original CAS, late-token receipts, the three-attempt budget, malformed representations, body/header bounds, cancellation, fail-closed missing admission state and an actual downstream catalog rollback preserving history. Clock tests vary host wall time independently of elapsed time, reject monotonic late completions, allow timely completion followed by delayed persistence, and recover both old and timed receipts after lease expiry or capture commit. Header-bound tests also verify that valid Retry-After survives metadata overflow, including mixed date/delta forms under host skew and a finite deadline for extreme numeric values. These tests count actual fake-handler sends and inspect retained rows. HTTP responses are fake and recovery tests seed durable checkpoints rather than terminating a process. Network/database connection outage and process-termination fault injection remain separate integration checks; removing the admission singleton exercises missing admission state without simulating a network outage.

The [recorded local MusicBrainz integration](../../../research/2026-10-17-full-normalization/scale/evidence/musicbrainz-acquisition-local-v1.json) reconciles eight CLI invocations, five commands, five GET responses and four captures in a dedicated local database. It covers a real retained 503 followed by an explicit resumption to 200, terminal replay and a separate cache-hit command. All 48 manifest-listed artifacts match their byte counts and hashes. The 503 was admitted on time but remained an HTTP failure with no capture; admission eligibility does not mean representation acceptance. The receipts establish no automatic retry scheduling or unconditional wire-level timing guarantee.

The refreshed work advanced from generation 1 to 2 because its JSON object-property order changed. Both payloads have the same values and array order; their decoded observations differ only in immutable input-revision references. This verifies retention and decoding without establishing a factual update, catalog link or automatic identity acceptance. The run made no production writes. The receipt records exact hashes, timestamps and the limits of the independent filesystem review.

Apply migrations 43 and 47 before enabling the current acquisition binary, including lookup-only callers: shared command reads now require the immutable request-kind discriminator. Migration 43 owns receipt/admission storage; migration 47 distinguishes lookup/search headers without replacing history. The shared registration adds the named client and scoped service to API and worker hosts; it starts no acquisition schedule or backfill. `Normalization:MusicBrainz` configures UserAgent and bounded timing options. All controlled callers sharing an egress must use the same primary gate database.

For binary rollback, stop acquisition callers first and retain commands, attempts, responses and the admission row. Do not rewind input generations, clear a live gate, delete failure receipts, or use an older caller to bypass the gate. Already captured evidence and independently published normalization remain durable. Search acquisition, a search-page decoder and the bounded local operator now exist under their [separate contract](musicbrainz-candidate-search.md). Candidate hydration and independently evaluated catalog correspondence/resolution remain required; lookup or search success activates no acceptance policy. The local integration does not replace the outage and process-termination checks described above.

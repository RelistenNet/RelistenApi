# Save signed-in plays to the listener's account

Status: server implementation and local verification complete. Mobile upload
and rollout are pending. This plan replaces Milestone 5 of the
[July implementation plan](2026-07-18-relisten-identity-user-data-and-sonos-implementation.md),
Slice 3 of the
[mobile-first delivery plan](2026-07-18-relisten-mobile-first-account-delivery-plan.md),
and the history sections of the July architecture document. Uploads may reach
external users only after [account deletion](2026-11-18-account-deletion.md) ships.

## Purpose / Big Picture

When a signed-in listener plays a track past the existing threshold (240 seconds
or half the track), the app saves that play to their account, including the
playlist entry it came from. Each device still shows only its own history. Reading
history across devices, rollups and yearly summaries come later and read from this
table.

Every signed-in play counts exactly once toward anonymous popularity in
`public.source_track_plays`. Signed-in plays reach it through the User Service
instead of `/live/play`. Signed-out plays keep using `/live/play`, which has no
play ID, so a retry after a lost response there can still count twice. That's
accepted for anonymous listening statistics.

## Context and Orientation

- Mobile creates a Realm `PlaybackHistoryEntry` when a play crosses the threshold
  (`relisten/player/relisten_player.tsx`, `updateConfirmedProgress`) and reports
  it through `/live/play` (`relisten/playback_history_reporter.ts`).
  - Each row has a client-generated `uuid`, `createdAt` and `playbackStartedAt`.
  - `publishedAt` marks a row as sent.
  - The reporter drains unsent rows in order and retries the first failure every
    30 seconds. A failed *immediate* send doesn't arm that timer today, so the
    row waits for the next reconnect.
  - Today `/live/play` receives only the track ID.
- **Two plays can come from one playback today.** The threshold check compares
  the previous progress with the new one. Seeking back below the threshold and
  crossing it again dispatches a second event with a new UUID.
- The device setting `TrackListeningHistorySetting` stops new rows from being
  created. Reconnecting still drains rows that were already unsent.
- `public.source_track_plays` is a compressed TimescaleDB hypertable with about
  254 million rows since 2018 and about 2.3 million a month. The two services
  share the `app` database role, so the User Service can already insert into it.
  The rule that this is its only catalog write is a code convention.
- Account data uses typed IDs: a prefixed TypeID wrapping a UUIDv7, stored as
  `text` (`AccountIdValidation` in `Relisten.Accounts.Contracts`). The Realm
  history row's existing `uuid` comes from `randomUUID()`, a v4 UUID, so it
  can't be a play ID.
- The mobile clear-history dialog currently says it permanently deletes listening
  history. That stays true only for the device copy.
- `user_data.history_generation` already exists, but it is unrelated. It is the
  server-wide playlist-sync generation that rotates on a database restore.

## Plan of Work

### 1. Table

Create `user_data.plays` as a hypertable on `qualified_at` with 90-day chunks:

| Column | Type | Meaning |
|---|---|---|
| `user_id` | text | `user_` ID. Foreign key to `identity.users`, `ON DELETE CASCADE` |
| `play_id` | text | `play_` UUIDv7 ID, generated by mobile. One per playback |
| `qualified_at` | timestamptz | The Realm row's `createdAt`: when the play crossed the threshold, by the device clock |
| `started_at` | timestamptz | The Realm row's `playbackStartedAt` |
| `received_at` | timestamptz | Server time of the first accepted upload |
| `track_id` | text | Catalog `track_` ID, as sent |
| `playlist_id` | text, nullable | `playlist_` ID when played from a playlist. No foreign key |
| `playlist_entry_id` | text, nullable | `playlist_entry_` ID of the entry played. No foreign key |
| `catalog_duration_ms` | integer, nullable | Track duration when playback started |
| `app_type` | smallint | Same values as `source_track_plays.app_type` |
| `offline` | boolean | Whether the track played from a download |
| `origin` | smallint enum | `live` (1) or `anonymous_import` (2) |

Add a unique key on `(user_id, qualified_at, play_id)`. It makes uploads
idempotent and serves per-user, time-ordered reads. Enable compression with
`segmentby = user_id`, ordered by `qualified_at DESC`. TimescaleDB 2.28 has
regression tests for `ON CONFLICT` into compressed chunks and for
`ON DELETE CASCADE` on a compressed segment key. Verify both against this schema,
and measure ingest before choosing the compression delay.

There are no receipts, per-user history state, play generations or rollups.

### 2. Upload

Add `POST /v1/history/plays:batch` to the User Service with
`{contract_version, plays: [...]}`, at most 500 plays. A malformed envelope gets
`422`. Each play is then checked on its own:

- `play_id` is a well-formed `play_` UUIDv7 ID.
- `track_id` is a well-formed catalog `track_` ID. It wraps the catalog's
  existing UUID, whatever its version, so it is checked with the catalog
  identifier parser, not `AccountIdValidation`. The User Service doesn't read catalog
  tables, so it doesn't check that the track exists.
- `started_at <= qualified_at`.
- `qualified_at` is no more than one day in the future and no more than 24 months
  in the past. This also stops a bad device clock from creating far-off chunks.

A play that fails a check is `rejected` and stored nowhere. One bad play must not
block the rest of the device's queue. If the same `play_id` appears twice in one
batch, only the first counts and the rest are `duplicate`. Then, for the valid
plays, run one transaction:

1. `INSERT … ON CONFLICT DO NOTHING RETURNING *` into `user_data.plays`.
2. For each returned row with `origin = live`, insert one row into
   `public.source_track_plays` with the UUID decoded from its `track_id`, its
   app type, `created_at = received_at`, and a null client UUID. Use
   `received_at`, not `qualified_at`. The hourly and daily popularity aggregates
   only revisit the last six hours and three days, so a week-old offline play
   stamped with `qualified_at` would never be counted. Popularity counts it on
   the day it uploads, as `/live/play` already does. Personal history keeps
   `qualified_at`. This is the User Service's only write to a
   catalog table, and it reads none. Unlike `RecordPlayableTrack`, it doesn't
   check that the track is playable. Only signed-in clients can call it.

`anonymous_import` plays never write an anonymous row, because the old app already
reported them through `/live/play`. A retried play is skipped in step 1, so it
can't double-count popularity.

Return each play's result as `accepted`, `duplicate` or `rejected`. Mobile marks
all three as sent. On a transient failure such as a `503`, mobile keeps the
rows pending and retries the same plays.

#### Server contract

The endpoint uses the existing library write authorization. Send
`contract_version: 1` and a `plays` array. Each item takes the fields from the
table above, except `user_id` and `received_at`, which the service supplies.
Send `origin` as `"live"` or `"anonymous_import"` and `app_type` as the existing
play smallint (0 unknown, 1 iOS, 2 web, 3 Sonos, 4 Android). The optional
playlist IDs and duration may be omitted or null.

The `200` body is `{contract_version, results: [{play_id, status}, ...]}`.
Results match request order. A rejected item with an invalid ID has
`play_id: null`. The first occurrence of a valid ID in a batch claims that
position, and repeats receive `duplicate`. Across requests, retry with the
same `qualified_at` and `play_id` so the account play and anonymous count
deduplicate together.

The accounts migration requires TimescaleDB and a connection to the shared
database containing `public.source_track_plays`. Deploy the migration and
account deletion before releasing the mobile writer. The User Service build
serves uploads as soon as it is deployed.

The migration configures the columnstore without scheduling automatic
compression. In a disposable TimescaleDB 2.28.2 database, ten 500-play SQL
batches per mode had median times of 8.3 ms into rowstore and 10.5 ms into a
compressed chunk. Each batch also wrote its 500 anonymous plays. This
single-listener sample checks that late ingest works. Choose the compression
delay after measuring the rollout workload.

### 3. Mobile

- **One play per playback.** Dispatch at most one play per playback: per queue
  occurrence and `playbackStartedAt`. Seeking back below the threshold and
  crossing it again must not create a second row.
- **Each row is bound to one destination when it is created.** Record the
  account signed in at that moment, or none. A row with an account is sent only
  to that account's batch endpoint, and only while that account is signed in.
  Otherwise it waits. A row with no account goes to `/live/play` as today. A row
  never switches destination, so a send whose outcome is unknown retries
  against the same endpoint. Only the account endpoint deduplicates those
  retries. `/live/play` can count a retried play twice.
- **Play IDs.** When mobile creates a row, it also generates a `play_` UUIDv7 ID
  and stores it in a new `playId` field. A row created before this change gets
  one the first time it is sent, written to Realm before the request goes out,
  so every retry reuses it.
- **What gets sent.** Send `play_id`, `track_id`, `qualified_at` (`createdAt`),
  `started_at` (`playbackStartedAt`), `playlist_id` and `playlist_entry_id`
  when the queue item came from a playlist, and the other table fields. Use the
  same values on the first send, every retry, after a restart and during import.
- **Retries.** Send in order. Retry a failed batch on the 30-second timer,
  including a failed immediate send, which doesn't arm the timer today.
- **Account deletion.** On deletion's `202`, an account's unsent rows are
  discarded with the rest of its data. On a `401`, they stay hidden, like the
  rest of that account's data.
- **History setting off.** Turning the setting off also discards every unsent
  row, for an account or not, so nothing recorded before the change uploads
  later.
- **Copy.** Change the clear-history confirmation to say it clears history on
  this device, and that plays saved to the account remain until the account is
  deleted.
- **Later step: import.** Offer a one-time import of existing device history
  after an explicit confirmation. It sends at most 24 months and 25,000 plays,
  all marked `anonymous_import`. Import only rows with no account and a
  `publishedAt`, meaning `/live/play` already counted them. Unsent anonymous rows
  keep going to `/live/play`.

## Validation and Acceptance

- Uploading the same batch twice stores each play once and writes one anonymous
  row per live play. A batch that repeats a `play_id` stores it once.
- An `anonymous_import` batch leaves `source_track_plays` unchanged.
- A well-formed track ID that isn't in the catalog stores the user play and its
  anonymous row. The hourly and daily popularity rollups and the v4 live feed
  leave it out.
- A batch with one malformed `track_id` or one out-of-range time stores the other
  plays and returns `rejected` for that one.
- Sign out of account A with an unsent row, then sign in as B. The row is not
  sent to `/live/play` or to B. It uploads when A signs in again.
- Lose a batch response for account A, then switch to B and back. The retry
  returns `duplicate` and `source_track_plays` has one row.
- Seek back below the threshold and cross it again. One row is created.
- Return `503`, then recover the service, on a continuously connected device. The
  pending row uploads within 30 seconds.
- Turn history off with an unsent row, then reconnect. Nothing uploads.
- Inserting old plays into a compressed chunk succeeds and stays idempotent.
- Account deletion removes the user's plays. The deletion plan's schema test
  covers this.

## Known limitations

- The legacy `/live/history` feed applies its `LIMIT` before dropping plays whose
  track doesn't hydrate. A page made entirely of unknown tracks comes back
  empty, and a polling client can stall on it. Orphaned tracks already cause
  this, and unknown IDs from signed-in clients can add to it. The v4 live feed
  filters before its `LIMIT` and isn't affected.

## Not in this plan

- Server-side clearing of history and an account-wide on/off switch. Add them with
  cross-device history. A clear then also needs to stop an offline device from
  re-uploading plays from before the clear.
- Database roles that enforce the user and catalog boundary.
